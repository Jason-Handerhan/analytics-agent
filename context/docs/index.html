Executive Summary

This project leverages the Kaggle Instacart Market Basket Analysis dataset to build a machine learning-powered recommendation engine designed to populate a personalized, 5-slot reorder widget during active shopping sessions. Delivering relevant product suggestions drives profit lift through three key mechanisms: increasing Average Order Value (AOV) by encouraging supplementary purchases, boosting conversion rates via reduced friction, and mitigating customer churn through saved time and increased engagement.

The champion model—a Rank Reciprocal Fusion (RRF) ensemble of all base models (XGBoost Ranker & Classifier + LightGBM Ranker & Classifier)—achieved a 0.3674 Recall@5 on unseen test data. While this may seem modest, predicting nearly 37% of a customer's reorders within just five slots is powerful. The model's value becomes more evident when compared to a heuristic baseline (predicting the first five items from the prior cart), providing a 39.3% lift over the 0.2638 recall@5 for the heuristic approach.

Translating this performance into financial impact—using public Instacart SEC filings for baseline assumptions—this architecture generates an estimated $118M Annual Profit Lift compared to a "no widget" scenario, and $33.5M Annual Profit Lift over the heuristic approach.

BigQuery Dataform Pipeline & Feature Engineering

The foundation of this machine learning model is a modular, version-controlled (GitHub Repository) SQL transformation pipeline orchestrated within BigQuery using Google Cloud Dataform.

1. Pipeline Architecture & Transformation Strategy

The ELT workflow follows a structured medallion architecture (Bronze Source Declarations → Silver Cleansed & Building Block Tables → Gold Feature Tables) designed to handle tens of millions of rows with minimal execution time.

1.1 Base Analytical Table & Feature Calculation Strategy

At the core of the Silver layer is the base_analytical_table, which unifies all cleansed source tables (orders, products, aisles, departments, and order_products) into a single analytical foundation. Candidate features for ML modeling are calculated from the base analytical table across distinct grains:

  • User-Level (e.g., order pacing, basket sizes, organic affinity)
  • User-Category (e.g., aisle and department shares)
  • User-Product pairs (e.g., cumulative purchases, cart positions, day-of-week and time-of-day counts).

1.2 Candidate Skeleton & Anchor Order Strategy

To prevent data leakage, features are engineered using an "Anchor Order" strategy:

  • Anchor Order: For each user, an Anchor Order is selected as the point of prediction.
  • Candidate Skeleton: A candidate_skeleton maps users to all products they have purchased on or before the Anchor Order (the reorder candidate products).
  • Join to Candidate Skeleton: All feature aggregations (purchase frequencies, basket shares, temporal patterns, etc.) calculated from the base analytical table are joined to the candidate skeleton on the anchor order. This ensures all features include only data from the first order through the anchor order.
  • Join the Label: The label is then independently joined to the candidate skeleton on Anchor Order + 1, ensuring the label represents the next order.
  • Forward-Fill Imputation: Because candidate products are not ordered in every order, window functions using LAST_VALUE(... IGNORE NULLS) forward-fill behavioral metrics across subsequent orders up to the anchor order. This preserves historical context without introducing leakage.

2. Data Quality Assertions & Validation

Dataform assertions are configured within final_ml_features_table.sqlx to enforce data integrity, order sequence consistency, and cold-start logic prior to modeling:

  • Null Value Prevention: Enforces IS NOT NULL checks across all features except for user_product_cart_position_last_order (which inherently & intentionally has nulls)
  • Sequence Consistency: Verifies that anchor_order_number = (label_order_number - 1) to ensure the label always represents the order following the anchor order.
  • Cold-Start Threshold Enforcement: Asserts anchor_order_number > 4, ensuring only users with established purchase histories are included in the machine learning model. A fallback heuristic approach is recommended for cold starts.
  • Bounded Range Checks: Validates that ratios (e.g., user_organic_affinity_ratio, user_product_day_of_week_affinity) fall within [0.0, 1.0] and day-of-week/hour bounds stay within calendar limits.

2. Evaluation Metrics

To align technical optimization with business value, the modeling pipeline utilized a tiered evaluation framework across three phases:

  • Training & Tuning Metric (NDCG@5 / Average Precision): Baseline models utilized objectives tailored to their architectural frameworks and class imbalance:
    • GBDT Rankers (NDCG@5): Tree-based ranking algorithms natively perform better when using LambdaMART or pairwise objectives optimizing for NDCG. Restricting the training metric evaluation to K=5 ensures the trees prioritize finding relevant items within the bounds of the UI widget.
    • Binary Classifiers (Average Precision / PR-AUC): For non-ranking models, PR-AUC was selected as the training metric to manage class imbalance. This focused optimization on precision-recall trade-offs without inflating performance via true negatives.
  • Ensemble Weight Optimization Metric (NDCG@5): NDCG@5 was selected as the optimization objective for three key reasons:
    • Pipeline Consistency: It aligns with the evaluation metric used during ranker model training. Switching to an unaligned metric like Recall@5 during the blending phase could distort the rankings established by the base models.
    • Position-Aware Ranking: Position matters in a recommendation widget. NDCG@5 penalizes the model heavily if highly relevant items are placed to lower positions (e.g., position 4 or 5 instead of position 1), which directly improves user experience.
    • Shared-Window Recall Optimization: Because both metrics evaluate the exact same window length (K=5), maximizing NDCG@5 inherently forces the model to pull relevant items into the top 5 slots—effectively optimizing for Recall@5 (the primary driver of business value) while simultaneously sorting them in the highest-conversion order.
  • Model Selection Metric (Recall@5): While NDCG@5 fine-tunes item positioning within the widget, Recall@5 was chosen as the metric for model selection. From an e-commerce business perspective, capturing the target reorder product anywhere within the 5-item widget is the primary driver of customer conversion, friction reduction, and Average Order Value (AOV) growth.
  • Secondary Evaluation Metrics (Precision@5 & F1-Score@5): While Recall@5 serves as the primary business north star, Precision@5 and F1-Score@5 were tracked as secondary guardrail metrics. Monitoring these metrics ensured the models maintained a balanced precision-recall profile, providing a holistic view of model performance.

3. Base Model Architectures & Bayesian Hyperparameter Optimization

Four distinct base models were constructed to capture complementary patterns in customer behavior:

  1. LightGBM Ranker: Uses a lambdarank objective with ('metric': 'ndcg', 'eval_at': 5) evaluation (leaf-wise tree growth).
  2. LightGBM Classifier: Uses a binary objective with average_precision evaluation (leaf-wise tree growth).
  3. XGBoost Ranker: Uses a rank:ndcg objective with (eval_metric='ndcg@5') evaluation (level-wise tree growth).
  4. XGBoost Classifier: Uses a binary:logistic objective with aucpr evaluation (level-wise tree growth).

3.1 Hyperparameter Tuning Strategy

Given the scale of the dataset (18.9 million rows), the training strategy prioritized data volume over exhaustive hyperparameter tuning. This approach ensured the models could learn nuanced interactions across long-tail product categories. To remain pragmatic with compute resources and execution runtimes for a portfolio project, an Optuna Bayesian Search was deployed for 25 trials per model to optimize tree architecture. Prioritizing data volume on massive datasets frequently yields better generalization than squeezing out fractional gains through exhaustive search spaces. Key strategies include:

  • Tree Ceiling & Early Stopping (n_estimators = 2000): Setting a high tree limit provided sufficient capacity for models to converge. An early_stopping_rounds = 50 callback was implemented as a primary regularization mechanism, halting training at peak validation performance before the models could memorize noise.
  • Learning Rate (learning_rate = 0.05): A moderate learning rate was selected to prevent overfitting while maintaining practical execution runtimes on a 16 vCPU Agent Platform virtual machine.
  • Tree Depth Strategy (num_leaves vs. max_depth): For LightGBM models, num_leaves was tuned instead of maximum depth to leverage leaf-wise growth. For XGBoost models, max_depth was tuned to control level-wise growth, capped at 10 to mitigate overfitting from repetitive splits on identical features.
  • L2 Regularization (reg_lambda): EDA feature screening revealed that a small subset of features drove the majority of feature importance. Tuning reg_lambda penalized the model for over-splitting on these dominant features, forcing it to learn patterns from secondary signals.
  • Feature Sampling (feature_fraction / colsample_bytree): This was tuned to inject diversity across individual trees, improving overall ensemble regularization and generalization.
  • Minimum Split Gain (min_split_gain / gamma): Set to a baseline of 0.1 for classifier models. This acts as a conservative regularization threshold, preventing the models from creating complex branches for marginal gains.
⚖️ Class Imbalance & Class Weight Rationale (scale_pos_weight / is_unbalance):
Positive reorder labels comprise ~9% of the dataset. Given the overall scale of the training data, that 9% minority class still represents a significant volume of positive samples—allowing XGBoost and LightGBM to effectively learn patterns using default loss weights. To stay pragmatic with compute time and cloud costs, hyperparameter tuning focused primarily on tree shape rather than class weighting. However, because the model specifically targets the top 5 slots, experimenting with class weights could provide fine-grained ranking improvements at the very top of the list. Testing these hyperparameters is therefore recommended for future iterations.

4. Ensembling & Rank Reciprocal Fusion (RRF)

4.1 Mathematical Objective Alignment & LambdaMART Overview

To enable seamless blending, the loss objectives and gain parameters were aligned between base LightGBM and XGBoost ranker models. Setting ndcg_exp_gain = False in XGBoost forced both XGBoost and LightGBM rankers to evaluate reorder probability using linear gain, ensuring both architectures solved the same unified LambdaMART objective from different algorithmic angles.

💡 Understanding the LambdaMART Objective

In machine learning, standard classification models predict whether a customer will buy an item independently (Yes or No). However, in e-commerce recommendation widgets, items are not evaluated in isolation; they compete for a limited number of display slots (e.g., Top 5). LambdaMART is an industry-leading "Learning-to-Rank" algorithm designed specifically for this list-based competition.

1. What is a Gradient?

During training, a model makes predictions and measures its mistakes using a loss function. A gradient is simply the mathematical compass (the direction and magnitude of error) that tells the model how to adjust its parameters to reduce mistakes. In standard regression, if a model predicts 0.4 for an item that should be 1.0, the gradient tells it: "Increase this score by 0.6."

2. How LambdaMART Works (Pairwise Comparisons & ΔNDCG):

Instead of looking at one item at a time, LambdaMART evaluates pairs of items within a user's order. If Item A (which the user actually reordered) is ranked below Item B (which was not reordered), LambdaMART calculates a specialized ranking gradient called λij (Lambda):

λij = |ΔNDCG| ×
1 1 + esi − sj

Where:

  • (si − sj): Is the current difference in predicted scores between the correct item (i) and the incorrect item (j).
  • |ΔNDCG|: Is the exact change in the global NDCG metric if the positions of item i and item j were swapped.

3. What is a Gradient Update in LambdaMART?

A gradient update is the step the tree-boosting algorithm takes to fix ranking errors. Because the gradient λij is directly multiplied by |ΔNDCG|, mistakes at the top of the list cause massive penalties. If swapping two items at Rank 1 and Rank 2 significantly drops the NDCG score, LambdaMART generates a huge gradient update that forces the decision trees to push the reordered item up immediately. Conversely, ranking errors at position 20 generate tiny gradient updates because they do not affect the Top 5 widget.

4.2 Score Standardization via Reciprocal Rank Fusion (RRF)

Blending ranker outputs (raw margin scores) with classifier outputs (probabilities between 0 and 1) directly can distort predictions. To solve this, predictions were standardized using Reciprocal Rank Fusion (RRF).

RRF_Score =
1 60 + Ranki

where Ranki is the item's predicted rank for a target order and 60 is the standard smoothing constant. This maps all model outputs onto an identical, rank-aware scale.

utility_functions.py — Reciprocal Rank Fusion (RRF)
def compute_rrf_scores(df, models, group_cols, c=60):
    """
    Converts raw predictions into Reciprocal Rank Fusion scores.

    Parameters:
    -----------
    df : pd.DataFrame
        Dataframe containing raw predictions.
    models : list of str
        List of model prediction column names to convert.
    group_cols : list of str
        Columns defining the grouping level (e.g., user and order).
    c : int, default=60
        RRF constant parameter.

    Returns:
    --------
    pd.DataFrame
        Dataframe containing the original data plus new RRF score columns.
    """
    df_rrf = df.copy()
    for col in models:
        rank_series = df_rrf.groupby(group_cols)[col].rank(ascending=False, method='min')
        df_rrf[f'{col}_rrf'] = 1.0 / (c + rank_series)
    return df_rrf

This section evaluates the projected financial impact of implementing the machine learning reorder prediction models compared to two baselines: a "No Widget" baseline and a "Heuristic Model" baseline. Translating the primary evaluation metric (Recall@5) into estimated profit lift bridges the gap between model performance and business value.

⚠️ Portfolio Context & Disclaimer: Please note that these financial projections are intended solely to demonstrate business analytics and ROI estimation skillsets for the purpose of this portfolio project. In reality, Instacart's massive scale and success are largely driven by the fact that they have already implemented highly sophisticated recommendation engines. Therefore, this analysis does not represent a true real-world incremental impact for Instacart today, but rather illustrates the theoretical value of deploying such machine learning models from a hypothetical zero-baseline.
🛠️ Strategy (Test Data for Financial Projections): The financial evaluation is based exclusively on the test split (unseen holdout data) rather than the validation set. While hyperparameters and ensemble weights were optimized on the train/validation split, the validation set was still utilized for model selection. Calculating the financial impact on that same validation data could introduce selection bias and artificially inflate profit lift estimates. By evaluating the financial impact on the unseen test set, we ensure the most unbiased projection of actual production performance.

Cold Start Strategy

While the machine learning model is effective at predicting reorder behavior for established users, the pipeline filters out users with insufficient order history (users with fewer than 4 prior orders). To ensure a seamless and personalized shopping experience for new users, a heuristic-based fallback strategy should be employed to fill the 5 widget slots.

Dynamic Widget Fallback Logic

Scenario 1: True Cold Start (Zero Prior Orders)

If a user is placing their first order on the platform, no historical cart data exists. In this scenario, the widget populates with the 5 most popular products globally at that exact time.

Note: This assumes the introduction of dates/timestamps in the production data pipeline to calculate real-time trending items.

Scenario 2: Partial Prior Cart (< 5 Items) Hybrid Approach

If a user has order history but their previous cart contained fewer than 5 items, the system utilizes a hybrid approach. It first pulls all available items from the user's prior cart to maintain personalization. The remaining empty slots are then filled using the global most popular items (that are not already in the cart). This guarantees all 5 slots are monetized.

Scenario 3: Full Prior Cart (≥ 5 Items)

If the user's most recent cart contained 5 or more items, the widget bypasses the global popularity metrics. It mimics the baseline heuristic model by populating the widget with the top 5 items from their prior cart, maximizing personalization.

1. Next Steps to Production

Before a full production rollout, several critical validation and engineering steps must be completed:

  • Automated Data Ingestion: Replacing the static Kaggle dataset with an orchestrated Cloud Composer (Airflow) DAG to continuously ingest, validate, and load source data into the BigQuery Bronze layer.

  • Front-End Widget & Cold Start Implementation: The front-end user interface for the 5-slot widget must be built and integrated into the active shopping session. Concurrently, the dynamic cold start strategy outlined previously must be engineered into the application logic.
  • A/B Testing & Financial Impact Validation: Deploy the champion model in a controlled A/B test to a sample group of active users. This is a vital prerequisite to validate the current theoretical financial impacts. Specifically, the A/B test should track actual changes in Average Order Value (AOV), Conversion Rate, and Customer Churn against a control group.
  • Latency & Load Testing: Assess the model's real-time inference latency. The system must populate the widget seamlessly during peak traffic hours without disrupting the shopping experience.

2. Opportunities for Improvement

While the current champion model delivers substantial business value, there are multiple avenues to consider to further enhance performance and increase profit lift:

  • Widget UI Expansion (Top 10+): The champion model's Recall@5 scores in the high 0.3s represent strong performance within a strict constraint, but also indicate that roughly 60% of a user's reorders are left on the table. Expanding the UI to a horizontally scrolling Top 10 or Top 15 carousel would capture more reorders, increasing the financial lift without fundamentally changing the model architecture.
  • More Extensive Hyperparameter Tuning & Class Weighting: Allocating more computational resources to deeper, more exhaustive hyperparameter tuning—such as running Optuna trials for more iterations, exploring expanded tree architectures, or evaluating class-imbalance hyperparameters (scale_pos_weight in XGBoost and is_unbalance / scale_pos_weight in LightGBM)—could yield additional top-of-list ranking refinements. At the scale of a business like Instacart, even a slight improvement in Recall@5 could translate into significant profit increases.
  • Timestamps & Global Features: The current model is limited by the lack of dates/timestamps in the dataset. Accessing real-world date/time data would unlock powerful global features—such as tracking top-selling/trending products, modeling seasonal shifts, and calculating global average purchase cycles. This could substantially boost predictive power.
  • Real-Time "In-Session" Context: Incorporating the current state of a user's cart would enable dynamic recommendations. For example, if a user adds hot dogs to their cart mid-session, the model could recalculate predictions and push hot dog buns to the #1 rank based on real-time context.
  • Price & Promotion Features: Integrating item price histories, active promotions, and a user's historical response to discounts could improve model predictions (price fluctuations could influence customer reorder decisions).
